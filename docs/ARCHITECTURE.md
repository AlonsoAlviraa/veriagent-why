## 1. What v6.1 is

- **User.** An e-commerce ops or finance analyst at a mid-size online retailer.
- **Question.** "Why did KPI X drop?" (gross margin, conversion, on-time delivery, return rate) over a period.
- **Output.** An exportable **decision memo** (MD + PDF, plus JSON from the API) containing ranked causes with an estimated contribution, one **discarded alternative** with the row that refutes it, a **0–100 confidence** from a deterministic formula, **row-ID citations** for every claim, recommended actions, and limitations.

**Data.** A seeded generator (`scripts/make_data.py`, written during the build) produces a **synthetic, labelled** retailer dataset. It is exposed through Zetaris as 5 views: `v_orders`, `v_returns`, `v_tickets`, `v_logistics`, `v_promotions`.
- Each scenario plants known causes (for example a carrier SLA breach in one region, or a supplier cost increase on one category) plus a **trap**: a promotion whose dates coincide with the drop but whose affected SKUs and regions don't overlap with it.
- The ground truth is written to `eval/ground_truth.json` and is never read by the agents.

**Agents** (each has its own prompt, input/output schema, tools, authority and trace events):

| Agent | Model | Role and authority |
|---|---|---|
| Planner | `nemotron-3.5-super-vl-120b-a12b` (S2) | Writes 3–5 competing hypotheses and SQL plans into H-MEM. Revises the plan when the Evaluator sends work back |
| Retriever (Agentic, v6.3) | `nemotron-3.5-lightning-30b-a3b` (S1) tool loop + Zetaris | Per hypothesis: a mandatory seed tool, then up to 2 model steps that judge sufficiency and pick the next whitelisted tool (`segment_stats`, `drill_down`, `promotions_overlap`, `text_search`). No free-form SQL: tools render fixed Zetaris templates with validated args. Text search is hybrid BM25 + `nvidia/nemotron-3-embed-1b` fused by RRF. Caps 2 steps/hyp, 8 calls/round, 8000 tokens/round; any failure → deterministic policy. Every call is traced and written to H-MEM. Broadens the query on zero rows or a timeout (max 2) |
| **S1 Relevance Filter** | `nemotron-3.5-lightning-30b-a3b`, thinking off (S1) | Scores each chunk/row group in parallel and drops irrelevant ones. **Consolidates** SQL metrics and text chunks into one evidence context in H-MEM. This is Alonso's S1+S2 pattern from arq1/arq2 and v4 |
| Evidence Evaluator | `nemotron-3.5-lightning-30b-a3b`, thinking off (S1 verifier) | Marks each piece of evidence as supports / refutes / gap. **Runs its own Zetaris query** to confirm every number (SSE §5 "What was unique"). Sends work back to the Planner |
| **Cause Analyst** | `nemotron-3.5-super-vl-120b-a12b` (S2) | Connects findings across views, ranks causes, estimates each cause's contribution with a deterministic decomposition, and picks `top_cause_label` from the fixed taxonomy |
| Writer | `nemotron-3.5-super-vl-120b-a12b` (S2) | Writes the memo using only Evaluator-approved claims, each with row IDs |
| **Traceability Check** | deterministic code (no LLM) | Runs after the Writer and **reuses the eval checker** (`app/checks/claims.py`). For each claim: the cited row IDs exist; the numbers match the DB within tolerance (±0.5 pp for rates, ±1% for amounts); entity and period match. On failure it sends the claim back to the Cause Analyst (max 2). It decides what leaves the system |

**Why this isn't "one agent with many labels" (OR §7.3, AUP §1).** Only two model families are used, but each agent differs in:
- **inputs**: the Planner sees the question and the H-MEM summary; the S1 filter sees single chunks; the Evaluator sees evidence plus its own fresh Zetaris rows.
- **tools**: only the Retriever and the Evaluator query Zetaris; only the Traceability Check reads the DB checker.
- **output schemas** (hypotheses, relevance scores, verdicts, ranked causes, memo).
- **authority**: the Evaluator can send the Planner back, and the Traceability Check can reject the Writer's output.
- **trace events**, which show these handoffs and rejections.

Models are a cost/latency choice per role (System 1 = a small model with thinking off, System 2 = the large reasoning model), not the definition of the agents. `nemotron-3-super-120b-a12b` reached end of life on 19 Oct 2026 (per `nvidia_models.md` / CHECKLIST), so it isn't used.

**Loops and caps (bounded):**
- Evaluator → Planner: "trap refuted / gap: revise plan + requery", max 3 rounds.
- Traceability Check → Cause Analyst: "unsupported claim blocked → rewrite", max 2.
- Retriever self-retry: max 2.
- Timeouts: model calls 60 s, Zetaris 20 s, whole run 8 min.

**When a cap or the 8-minute timeout is hit:**
- The run returns a **partial memo** marked `"resolution": "unresolved"`, listing the hypotheses still open and the claims that were blocked.
- Confidence is **capped at 40**.
- The trace logs `status: "partial"`.
- The API returns HTTP 200 with `status: "partial"`. It never hangs or crashes (TER §2/§5).

**Confidence (deterministic, documented in README; the LLM never produces it):**
`conf = round(100 × (0.45·C + 0.35·A + 0.20·(1−R)))`
- **C** (coverage) = share of **all proposed claims** (including claims later blocked) that have ≥1 supporting row which passed the Traceability Check.
- **A** (cross-source agreement) = share of the 5 views whose direction agrees with the top cause, among views with relevant rows. **If no view has relevant rows, A = 0 and confidence is capped at 50.**
- **R** (refutation pressure) = refuting edges ÷ (supporting + refuting edges) for the top cause.
- Partial/unresolved runs are capped at 40.
- The weights (0.45/0.35/0.20) are a design choice **tuned on the 6 dev questions only** (a small sample, stated as such). They're frozen before the test run.

**What-if (labelled ESTIMATE):** the user can re-run the Cause Analyst's decomposition with one factor neutralized, for example "if carrier SLA in region N had stayed at baseline". It's a recalculation over the same rows, shown with an "ESTIMATE — model-based, not observed" badge. There is no World Model (v5C stays out).

**Meterless (load-bearing; the diagram shows read/write edges from the agents):**
- **H-MEM** is the evidence graph. The Planner writes hypotheses, the S1 filter writes consolidated evidence, the Evaluator writes verdict edges, and the Cause Analyst and Writer read from it: hypothesis → evidence → row-ID nodes, support/refute edges, an audit ledger that becomes the memo's citation list, and the consolidated SQL + text context.
- **Markovian** runs the multi-round investigation in chunks with carryover, and emits the **projected-versus-actual token report**. That report includes the tokens the S1 filter avoided sending to S2 (projected = all chunks, actual = after the filter), measured per run.
- Feature tests: `tests/test_hmem_graph.py` (invariant: every approved claim → ≥1 supporting edge → an existing row) and `tests/test_markovian.py`.

**Provider switch:** `LLM_PROVIDER=nightshift|nvidia|sample`. Nightshift is Nemotron through Meterless and is the default in the demo if it's reachable at 0 €. `nvidia` calls the NVIDIA API directly. `sample` runs offline using a rule-based planner, the deterministic filter (lexical score), and template-plus-computation writing. The provider is logged per call.

**Interface:** FastAPI `POST /run` → JSON (SSE §2 / TER §2 shape) on `:8000`, `GET /memo/{run_id}.md|.pdf`, and a light web UI on a **separate port** (`:8501`) that only calls the API (TER §2): question box, the evidence graph growing as trace events arrive, claim click-through to the Zetaris row, the confidence breakdown, and the what-if.

**SAMPLE_MODE:** a DuckDB snapshot generated by the same seeded script, queried with the same SQL. The whole pipeline runs offline from a clean clone with an empty `.env`. Real computation, no replayed outputs.

## 3. Eval plan (all figures measured, none invented)

**Freezing order:**
1. Fix the generator seed.
2. Generate all scenarios.
3. Write `eval/ground_truth.json` and `eval/splits.json`, and commit them with their hash.
4. Only then tune prompts and weights on dev.
5. Run test once per system for the reported numbers. Any re-run is reported with the reason.

**Set: 24 "why" questions.**
- **6 dev questions**, used for tuning. The **demo scenario (the promotion trap shown in the video) is in dev, never in test.**
- **18 test questions**, frozen, made up of:
  - ≥4 **promotion traps** (a promotion coincides in dates, but its SKUs/regions don't overlap with the drop) in scenarios different from the demo;
  - ≥4 **seasonality traps** (a drop explained by a seasonal baseline, which is not a cause);
  - ≥3 **negative controls**, where the promotion **is** the real cause (this checks that the system doesn't just learn "promotions are always traps");
  - the rest are plain planted causes (carrier SLA, supplier cost, pricing error, stock-outs).
- **Cause taxonomy (fixed list):** `carrier_sla`, `supplier_cost`, `pricing_error`, `stockout`, `promotion`, `seasonality`, `return_fraud`, `none_found`. `top_cause_label` must be one of these and is scored by **exact match**.

**Systems compared:**
- (a) **VeriAgent Why v6.1**.
- (b) **Plain-RAG baseline** with the same model (`nemotron-3.5-super-vl-120b-a12b`), the same provider, the same data (rows serialized as text with row IDs), the same questions, the **same max-token limit** and the **same output JSON schema** (including `top_cause_label`, claims and `row_ids`). It does top-k retrieval + one generation call, with no loops, no Evaluator, no S1 filter and no Traceability Check.

**Metrics:**
- **Cause accuracy:** top-1 exact-match on `top_cause_label`, reported as **k/18 with a Wilson 95% interval**. Top-2 is also reported.
- **Unsupported-claim rate:** share of the claims whose row IDs don't exist or whose numbers, entity or period don't match. It uses **the same checker as the Traceability Check** (`app/checks/claims.py`), run independently by `scripts/eval.py`. The baseline's **uncited share** (claims with no row IDs) is reported **separately** and also counted as unsupported in the main figure.
- **Trap-avoidance rate**, split by trap type, and **negative-control accuracy**, both as k/n with a Wilson interval.
- **Partial rate:** share of runs that ended "unresolved".
- **Time per answer** (median, p90) and **tokens per answer**.

**Reporting rules:**
- `eval/RESULTS.md` records the git SHA, model IDs, seed, splits hash and timestamps.
- Losses are reported. With n=18 the intervals will be wide, so differences are described as "observed", **never as "significant"**.
- Sample-mode (rule-based) results are reported separately.
- Synthetic-data caveat: "planted causes are easier than real life".

**Cost:** NVIDIA credits only; stop if the free credits run low.
